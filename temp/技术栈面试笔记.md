## 一、V4L2 与 DMA-BUF 零拷贝

### 1.1 V4L2 四种内存类型（高频考点）

| 类型 | 内存所有者 | 拷贝次数 | 用途 |
|------|-----------|---------|------|
| `V4L2_MEMORY_MMAP` | 内核驱动分配 | 零拷贝（mmap 映射） | 常规视频采集 |
| `V4L2_MEMORY_USERPTR` | 用户空间分配 | 至少一次拷贝 | 用户控制内存 |
| `V4L2_MEMORY_OVERLAY` | 显示硬件 | 零拷贝（硬件直写） | 视频叠加 |
| `V4L2_MEMORY_DMABUF` | 任意（共享） | 零拷贝（驱动间共享） | 跨设备硬件流水线 |

**MMAP vs DMABUF 的本质区别**：
- **MMAP** 解决「摄像头 → CPU/用户空间」的零拷贝（页表映射访问内核物理内存）。
- **DMABUF** 解决「摄像头 → GPU/编码器/另一进程」的**跨设备**零拷贝（fd 传递物理内存访问权）。

### 1.2 DMA-BUF 三大角色

- **导出者（Exporter）**：分配物理内存的驱动，`dma_buf_export` 导出 fd。
- **导入者（Importer）**：使用内存的驱动，`dma_buf_attach`/`dma_buf_map_attachment` 导入。
- **用户空间**：通过 fd 传"钥匙"，不传数据本身。

### 1.3 关键 ioctl

- `VIDIOC_EXPBUF`：从 V4L2 buffer 导出 dma_buf fd。
- `VIDIOC_QBUF`：把外部 dma_buf fd 填 `buf.m.fd` 入队。
- `VIDIOC_REQBUFS`：`memory = V4L2_MEMORY_DMABUF` 申请。

### 1.4 面试追问

- **videobuf2**：V4L2 内核侧缓冲区管理框架，统一管理三种内存模式的状态机（queued→active→done→queued）。
- **为什么物理连续内存**：DMA 引擎按物理地址访问，不经过 CPU MMU，需 `dma-contig`（物理连续）或 `dma-sg`（散列表）。
- **为什么选 NV12**：硬件编码器（MPP/VPU）直接支持，若摄像头输出 YUYV 需转换，破坏零拷贝链路。

## 二、RKNN INT8 量化与反量化

### 2.1 核心公式（仿射量化）

```
量化：  Q = round(R / scale) + zero_point
反量化：R = (Q - zero_point) × scale
```

- `R`：原始浮点值；`Q`：量化整数；`scale`：缩放因子；`zero_point`：零点偏移。
- RKNN 运行时的反量化实现：`f32_value = (raw_i8 - zero_point) * scale`。

### 2.2 对称 vs 非对称量化

- **对称量化**：`zero_point = 0`，计算简单，但要求数据分布关于零点对称，否则浪费一半整数范围。
- **非对称量化**：`zero_point` 任意，充分利用整数表示范围，适合偏态分布（如 ReLU 后 `[0,+∞)`）。
- **RKNN 默认用非对称量化**（`asymmetric_quantized-8`）。

### 2.3 scale / zero_point 计算

```
scale = (max_float - min_float) / (qmax - qmin)
zero_point = qmax - round(max_float / scale)
```

INT8 范围 `[-128, 127]`，uint8 范围 `[0, 255]`。

### 2.4 PTQ 量化流程（训练后量化）

1. 用代表性校准数据集（100~300 张图）跑 FP32 模型；
2. 统计每层激活/权重的动态范围；
3. 计算每层 scale/zero_point；
4. FP32 权重转 INT8，插入量化/反量化节点。

**量化误差来源**：取整误差（round 丢失精度）+ 截断误差（超出校准范围的被截断）。

## 三、FFmpeg RTMP 推流 / FLV / H.264

### 3.1 分层处理链路

```
协议层(RTMP) → 解协议 → 封装层(FLV) → 解封装 → 编解码层(H264/AAC) → 解码 → 像素层(YUV/PCM)
```

### 3.2 RTMP 关键约定

- RTMP 底层基于 **TCP**，三阶段模型（握手-连接-流控制），延迟 1~3 秒。
- **视频必须 H.264，音频必须 AAC/MP3，FLV 封包**。
- 音视频分开以 **Tag** 打包发送。

### 3.3 FLV 的 H.264 格式

- 视频 Tag 的 Payload 中 H.264 采用 **AVCC 格式**（每个 NALU 前 4 字节标大小），区别于 Annex-B（起始码 0x000001）。
- FLV 典型流结构：`SPS PPS SEI → I帧 → P帧 → ... → SPS PPS SEI → I帧`。

### 3.4 H.264 核心技术（面试必考）

- **帧内预测**（Intra）：当前帧相邻像素空间域预测，用于 I 帧。
- **帧间预测**（Inter）：帧间时间相关性，运动估计/补偿，用于 P/B 帧。
- **熵编码**：CABAC（算术编码，压缩率高）vs CAVLC（变长编码，复杂度低，实时用）。
- **多参考帧、可变块大小**。

### 3.5 NALU 类型表

| NAL type | 内容 |
|---|---|
| 1 | 非 IDR 图像片段 |
| 5 | IDR 图像（关键帧） |
| 6 | SEI（补充增强信息） |
| 7 | SPS（序列参数集） |
| 8 | PPS（图像参数集） |

- **IDR 帧**：GOP 起始关键帧，解码器遇 IDR 清空参考帧缓存。
- **GOP 结构影响首播时间**（I 帧间隔越大首屏越慢）。

### 3.6 协议延迟对比

| 协议 | 传输 | 封装 | 延迟 |
|---|---|---|---|
| RTMP | TCP 流 | FLV | 低（1~3s） |
| HTTP-FLV | HTTP 长连接 | FLV | 低（约 2s 内） |
| HLS | HTTP 切片 | TS | 高（10~30s） |

### 3.7 高频追问

- 帧内 vs 帧间预测区别；GOP 对首播时间影响。
- CBR / VBR / CRF 码率控制适用场景。
- 为什么视频会议不用 HLS（10~30 秒延迟不可接受）。
- DTS vs PTS 区别、音视频同步时钟策略。

## 四、C++ 多线程（atomic / CAS / mutex / shared_ptr）

### 4.1 shared_ptr 线程安全（三层回答，核心考点）

**结论：控制块（引用计数）线程安全，但 shared_ptr 实例本身和被管理对象都不安全。**

1. **控制块（引用计数）——线程安全**：内部用 `std::atomic` 的 `fetch_add`。增计数用 `memory_order_relaxed`，减计数用 `memory_order_acq_rel`（减到零要释放对象，需保证其他线程写入可见）。
2. **shared_ptr 实例本身——不安全**：多线程同时**读**同一实例安全；但只要有线程**写**（reset/赋值/移动）必须加锁。因为 shared_ptr 有两个数据成员（指针 + 计数），拷贝赋值两步操作不能原子化。C++20 提供 `std::atomic<std::shared_ptr<T>>`。
3. **被管理对象——不安全**：shared_ptr 只管生命周期，对象内部并发访问要对象自身加锁。

**安全做法**：
1. 每个线程持有自己的 shared_ptr 副本（值传递，拷贝时原子 +1）。
2. 修改全局 shared_ptr 用 mutex，或 C++20 `atomic<shared_ptr>`。
3. 对象内部并发访问需对象自身加锁。

### 4.2 CAS 原理

CAS 三个操作数：内存位置 V、预期值 A、新值 B。若 V==A 则写 B，否则不做。失败时循环重试。

```cpp
while(1) {
    eax = val;          // 取当前值
    if (eax == V) {     // 比较
        eax++;
        V = eax;        // 更新
        break;
    }
}
```

**应用**：计数器、标志位、轻量级锁。**注意**：多个原子操作的组合不一定线程安全，原子性只针对单操作。

### 4.3 mutex 与锁

- `lock()`：阻塞式，失败挂起（上下文切换，开销大）。
- `try_lock()`：非阻塞，失败返回 false，配 `yield()` 减少忙等。
- `lock_guard`/`unique_lock`：RAII 自动解锁。

### 4.4 weak_ptr::lock() 的 CAS

弱引用转强引用必须原子：检查强计数不为 0 才递增强计数，防止「检查后、递增前对象被销毁」的 TOCTOU 问题。用 CAS 循环实现。

## 五、RK3568 部署（MPP / RGA / NPU）

### 5.1 三大硬件模块分工

```
FFmpeg（拉流/解封装）→ MPP（硬解码）→ RGA（预处理）→ RKNN/NPU（推理）→ 画框 → MPP（编码）→ FFmpeg（推流）
```

| 模块 | 职责 |
|------|------|
| MPP | 硬件编解码（H.264/H.265），统一 MPI 接口 |
| RGA | 2D 加速：格式转换、缩放、裁剪（NV12→RGB） |
| NPU/RKNN | AI 推理，加载 .rknn 模型 |

### 5.2 MPP 核心

- **MppPacket**：一包编码数据（H.264 NALU）。
- **MppFrame**：一帧解码图像（宽高、格式、stride）。
- **内存**：必须用 MppBuffer（DMA-BUF/IOMMU 硬件友好内存），malloc 可能花屏。
- 流程：`mpp_create → 配置 → 输入 → 取结果 → 销毁`。

### 5.3 RGA 核心

- 导入/封装：CPU 内存用 `importbuffer_virtualaddr`/`wrapbuffer_virtualaddr`，dma-buf 用 `wrapbuffer_fd`（V4L2/硬编 DMA buffer 零拷贝共享）。
- 指定源/目标格式（`RK_FORMAT_YCbCr_420_SP` → `RK_FORMAT_RGB_888`）。
- buffer 大小 = `width × height × bpp`。
- 坑：不能对 V4L2 的 dma-coherent buffer 用 `wrapbuffer_virtualaddr`，否则 RGA2 用自身 MMU 重映射失败（"RGA_BLIT fail: Invalid argument"）；本项目 V4L2 帧走 fd、mp4 帧走虚拟地址。

### 5.4 面试高频

- 为什么硬件编解码：高性能、低功耗。
- 数据流格式变化：压缩码流(Packet) → YUV 帧(Frame) → RGB → 张量(Tensor) → 画框后重新编码。
- 内存与同步是工程关键。

## 六、YOLOv5 后处理 / NMS / Anchor / Letterbox

### 6.1 输出张量结构

输入 `[1,3,640,640]`，输出 `[1,25200,85]`：
- `25200 = (80×80 + 40×40 + 20×20) × 3`（三个尺度 × 3 anchor）。
- `85 = (cx,cy,w,h,obj_conf) + 80 cls_conf`。

后处理三步：
1. 目标置信度过滤：`obj_conf > conf_thres`。
2. 类别置信度过滤：`obj_conf × max(cls_conf) > conf_thres`。
3. NMS 过滤（按类别分别执行）。

最后把框从 640×640 还原回原图。

### 6.2 NMS 步骤

1. 按置信度降序排序。
2. 取最高分框为基准框。
3. 计算其他框与基准框的 IoU。
4. 移除 IoU > 阈值（0.5~0.7）的框。
5. 重复直到无框可处理。

**NMS 需每个类别分别执行**。变种：DIOU-NMS、Soft-NMS。

### 6.3 Anchor

- 预先设定的不同大小/长宽比的参照框，引入先验，帮助收敛。
- YOLOv5 共 9 个 anchor，3 个 Detect 层，每 cell 3 个。
- 大特征图（小感受野）配小 anchor 测小目标。
- 由 K-means 聚类 + 遗传算法优化得到。

### 6.4 Letterbox

- 计算两个 resize 比例，取**最小比例**（长边到 640）。
- 短边差值除以 stride 取余再除 2，得填充宽度。
- 灰边填充，保持宽高比不变形。

### 6.5 损失函数

`总损失 = 分类损失 + 定位损失（GIOU）+ 置信度损失`。
