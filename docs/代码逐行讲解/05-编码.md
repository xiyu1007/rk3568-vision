# 05 — 编码（H.264 软编 + MPP 硬编）

本篇讲两个编码器：`src/h264_encoder.cpp`（libx264 软编）和 `src/mpp_encoder.cpp`（Rockchip MPP 硬编）。两者接口一致，Pipeline 按「硬编优先、失败回退软编」切换。

---

## 5.1 为什么有两个编码器

- **软编（libx264）**：用 CPU 编码，跨平台、灵活，但 CPU 占用高（35~40%）、延迟较高（15~25ms）。
- **硬编（MPP）**：用 Rockchip 专用硬件编码器，CPU 占用低（~5%）、延迟低（~4ms），但依赖特定芯片。

策略：`encode.hardware=true` 时先试硬编，硬编打不开（如 x86 无 MPP）自动回退软编。

---

## 5.2 `h264_encoder.cpp` — libx264 软编

### 5.2.1 Open（打开编码器）

```cpp
bool H264Encoder::Open(const EncodeConfig& config, uint32_t width, uint32_t height, uint32_t fps) {
    // 1. 选编码器：硬编优先，失败回退软编
    if (config.hardware) {
        codec_ = avcodec_find_encoder_by_name("h264_rkmpp");   // 找 rkmpp（旧方案，板端没有）
        if (codec_) hardware_ = true;
        else warn("h264_rkmpp not found, fallback libx264");
    }
    if (codec_ == nullptr) {
        codec_ = avcodec_find_encoder(AV_CODEC_ID_H264);   // libx264
        hardware_ = false;
    }

    // 2. 配置上下文
    codec_context_ = avcodec_alloc_context3(codec_);
    codec_context_->width  = width;
    codec_context_->height = height;
    codec_context_->time_base = {1, fps};           // 时间基 1/fps（pts 单位）
    codec_context_->framerate = {fps, 1};
    codec_context_->bit_rate  = config.bitrate;
    codec_context_->gop_size  = config.gop_size;    // 关键帧间隔
    codec_context_->max_b_frames = 0;               // 零 B 帧，降延迟
    codec_context_->pix_fmt = AV_PIX_FMT_YUV420P;   // 软编吃 YUV420P
    codec_context_->flags |= AV_CODEC_FLAG_GLOBAL_HEADER;  // SPS/PPS 放 extradata

    if (!hardware_) {
        av_opt_set(codec_context_->priv_data, "preset", "ultrafast", 0);
        av_opt_set(codec_context_->priv_data, "tune",   "zerolatency", 0);
    }
    avcodec_open2(codec_context_, codec_, nullptr);

    // 3. 分配目标帧 + sws 转换上下文（NV12 → YUV420P）
    dst_frame_ = av_frame_alloc();
    dst_frame_->format = AV_PIX_FMT_YUV420P;
    av_frame_get_buffer(dst_frame_, 32);
    sws_context_ = sws_getContext(width, height, AV_PIX_FMT_NV12,
                                  width, height, AV_PIX_FMT_YUV420P, SWS_FAST_BILINEAR, ...);
}
```

**逐行讲解（编码的每个关键参数）**：
- `avcodec_find_encoder_by_name("h264_rkmpp")`：这是旧方案的硬编（FFmpeg 的 rkmpp 插件）。**板端 FFmpeg 没有这个**，所以实际回退到 libx264。现在硬编用的是 MPP（mpp_encoder.cpp），不走这里。
- `time_base = {1, fps}`：时间基是 1/25 秒，所以 pts=0,1,2... 每帧 1/25 秒。这是**帧序号当时间戳**的简化做法。
- **`max_b_frames = 0`**：禁用 B 帧。B 帧是双向预测帧，要参考前后帧，编码器要等后续帧才能编，**引入延迟**。禁用后只有 I/P 帧，延迟低。
- `AV_CODEC_FLAG_GLOBAL_HEADER`：把 SPS/PPS 写到 `extradata`（AVCC 格式），而不是塞进码流（Annex-B）。FLV/RTMP 需要 AVCC。
- **`preset = "ultrafast"`**：x264 的速度预设，ultrafast 最快（牺牲压缩率换速度）。
- **`tune = "zerolatency"`**：零延迟调优，关掉 lookahead（前瞻），编码器不等后面的帧，实时性最好。
- `pix_fmt = YUV420P`：libx264 吃 YUV420P（planar 三平面），而采集是 NV12（两平面），要用 sws_scale 转。
- `av_opt_set(priv_data, ...)`：设置 x264 私有参数（preset/tune 不是 FFmpeg 通用参数，是 x264 特有的，所以设 priv_data）。

### 5.2.2 Encode（编码一帧）

```cpp
bool H264Encoder::Encode(const FramePtr& frame, callback) {
    if (hardware_) {
        // 硬编：NV12 零拷贝直通
        dst_frame_->data[0] = frame->nv12_data;
        dst_frame_->data[1] = frame->nv12_data + frame->nv12_stride * height_;
    } else {
        // 软编：NV12 → YUV420P
        av_frame_make_writable(dst_frame_);
        const uint8_t* src[2] = { frame->nv12_data, frame->nv12_data + stride*height };
        sws_scale(sws_context_, src, src_linesize, 0, height, dst_frame_->data, dst_frame_->linesize);
    }

    dst_frame_->pts = pts_++;                  // 帧序号当时间戳
    avcodec_send_frame(codec_context_, dst_frame_);

    while (true) {
        PacketPtr packet = CreatePacket();
        if (avcodec_receive_packet(codec_context_, packet.get()) == 0) {
            on_packet(packet);                 // 回调交出编码包
        } else break;
    }
}
```

**逐行讲解**：
- 软编路径：`sws_scale` 把 NV12 转 YUV420P（NV12 的 Y 平面 + 交错 UV 平面 → YUV420P 的 Y + U + V 三平面）。
- `dst_frame_->pts = pts_++`：帧序号递增，作为时间戳。
- **`avcodec_send_frame` + `avcodec_receive_packet`**：这是 FFmpeg 新版的**推拉模型**（send/receive），一帧可能产 0~N 个包（B 帧会延迟，无 B 帧则 1 帧 1 包）。`while` 循环把该帧产的所有包都取出来。

**面试点**：为什么用 send/receive 模型？这是 FFmpeg 3.1+ 的新 API，替代旧的 `avcodec_encode_video2`，支持更灵活的编码控制（一帧多包、延迟、flush）。

### 5.2.3 Flush（冲刷残留帧）

```cpp
void H264Encoder::Flush(callback) {
    avcodec_send_frame(codec_context_, nullptr);   // 送 nullptr 表示"没有更多帧了"
    while (true) {
        PacketPtr packet = CreatePacket();
        if (avcodec_receive_packet(codec_context_, packet.get()) == 0) on_packet(packet);
        else break;
    }
}
```

**逐行讲解**：`send_frame(nullptr)` 告诉编码器"没有更多输入了"，让它把内部缓冲的残留帧（延迟的 B 帧等）全部输出。编码器内部有缓冲，最后要冲刷。

## 5.3 `mpp_encoder.cpp` — MPP 硬件编码

### 5.3.1 Open（创建 MPP 上下文 + 配置）

```cpp
bool MppEncoder::Open(config, width, height, fps) {
    // 1. 创建 MPP 上下文
    mpp_create(&ctx_, &mpi_);
    // 2. 初始化为 H.264 编码器
    mpp_init(ctx_, MPP_CTX_ENC, MPP_VIDEO_CodingAVC);

    // 3. 配置编码参数（字符串 key + 值）
    MppEncCfg cfg;
    mpp_enc_cfg_init(&cfg);
    mpp_enc_cfg_set_s32(cfg, "prep:width", width);
    mpp_enc_cfg_set_s32(cfg, "prep:height", height);
    mpp_enc_cfg_set_s32(cfg, "prep:format", MPP_FMT_YUV420SP);   // NV12
    mpp_enc_cfg_set_s32(cfg, "rc:mode", MPP_ENC_RC_MODE_CBR);    // 固定码率
    mpp_enc_cfg_set_s32(cfg, "rc:bps_target", bitrate);
    mpp_enc_cfg_set_s32(cfg, "rc:gop", gop);
    mpp_enc_cfg_set_s32(cfg, "rc:fps_in_num", fps);
    mpp_enc_cfg_set_s32(cfg, "codec:type", MPP_VIDEO_CodingAVC); // H.264
    mpp_enc_cfg_set_s32(cfg, "codec:profile", 100);              // high profile
    mpi_->control(ctx_, MPP_ENC_SET_CFG, cfg);
    mpp_enc_cfg_deinit(cfg);

    // 4. 头信息（SPS/PPS）单独获取
    MppEncHeaderMode header_mode = MPP_ENC_HEADER_MODE_DEFAULT;
    mpi_->control(ctx_, MPP_ENC_SET_HEADER_MODE, &header_mode);

    // 5. 输入 buffer 组（DRM 内存）
    mpp_buffer_group_get_internal(&buf_group_, MPP_BUFFER_TYPE_DRM);

    // 6. 取 SPS/PPS
    PrepareExtradata();
}
```

**逐行讲解**：
- `mpp_create` / `mpp_init(MPP_CTX_ENC, MPP_VIDEO_CodingAVC)`：创建并初始化为 H.264 编码器。
- **配置用"字符串 key + 值"**：`mpp_enc_cfg_set_s32(cfg, "prep:width", w)`。这是 MPP 特有的配置方式，key 是字符串（如 "prep:width"、"rc:bps_target"）。好处是配置项很多时不改函数签名，坏处是 key 拼错编译不报错、运行时才出错。
- `MPP_ENC_RC_MODE_CBR`：CBR（恒定码率）码率控制。
- `MPP_FMT_YUV420SP`：NV12 格式（Y + 交错 UV）。
- `codec:profile = 100`：H.264 high profile。
- `MPP_BUFFER_TYPE_DRM`：输入 buffer 用 DRM 内存（DMA-BUF 的一种）。
- `PrepareExtradata`：取 SPS/PPS，转成 AVCC 格式给封装器。

### 5.3.2 Encode（编码一帧）

```cpp
bool MppEncoder::Encode(const FramePtr& frame, callback) {
    // 1. 从 buffer 组取一块内存，拷贝 NV12
    const size_t frame_size = width_ * height_ * 3 / 2;
    MppBuffer buffer;
    mpp_buffer_get(buf_group_, &buffer, frame_size);
    void* ptr = mpp_buffer_get_ptr(buffer);
    memcpy(ptr, frame->nv12_data, frame_size);   // 这里有一次拷贝！

    // 2. 构造 MppFrame 并提交
    MppFrame mframe;
    mpp_frame_init(&mframe);
    mpp_frame_set_width/height/hor_stride/ver_stride/fmt/buffer/pts...
    mpi_->encode_put_frame(ctx_, mframe);    // 异步提交
    mpp_frame_deinit(&mframe);

    // 3. 取编码结果
    MppPacket packet;
    while (mpi_->encode_get_packet(ctx_, &packet) == MPP_OK) {
        void* data = mpp_packet_get_pos(packet);
        size_t len = mpp_packet_get_length(packet);
        EmitAnnexBPacket(data, len, pts, callback);   // Annex-B 转 AVCC
        mpp_packet_deinit(&packet);
    }
}
```

**逐行讲解**：
- **注意这里有 memcpy**：MPP 需要把 NV12 拷贝到它自己分配的 DRM buffer 里。这不是完全零拷贝（真正的零拷贝要用 `importbuffer_fd` 把 V4L2 的 fd 导入，但当前实现为了简单用 memcpy）。这是可以优化的点。
- `encode_put_frame` / `encode_get_packet`：异步提交/取回（put 后不一定立刻能 get）。
- `EmitAnnexBPacket`：MPP 输出 Annex-B，转成 AVCC。

### 5.3.3 Annex-B → AVCC 转换

```cpp
// 找下一个 Annex-B 起始码（00 00 01 或 00 00 00 01）
int FindStartCode(const uint8_t* data, size_t size, size_t* code_len) {
    for (size_t i = 0; i + 3 <= size; ++i) {
        if (data[i]==0 && data[i+1]==0 && data[i+2]==1) { *code_len = 3; return i; }
        if (i+4<=size && data[i]==0 && data[i+1]==0 && data[i+2]==0 && data[i+3]==1) { *code_len = 4; return i; }
    }
    return -1;
}

void MppEncoder::EmitAnnexBPacket(const uint8_t* data, size_t size, int64_t pts, callback) {
    PacketPtr av_pkt = CreatePacket();
    av_pkt->pts = pts;
    av_pkt->dts = pts;

    std::vector<uint8_t> avcc;
    ParseAnnexB(data, size, [&](const uint8_t* nal, size_t len) {
        // 每个 NAL：写 4 字节长度前缀 + NAL 数据
        avcc.push_back((len >> 24) & 0xFF);
        avcc.push_back((len >> 16) & 0xFF);
        avcc.push_back((len >> 8)  & 0xFF);
        avcc.push_back(len & 0xFF);
        avcc.insert(avcc.end(), nal, nal + len);
    });
    av_pkt->data = av_malloc(avcc.size());
    memcpy(av_pkt->data, avcc.data(), avcc.size());
    av_pkt->size = avcc.size();
    on_packet(av_pkt);
}
```

**逐行讲解（Annex-B vs AVCC，面试重点）**：
- **Annex-B**：H.264 码流的传统格式，每个 NAL 用起始码 `00 00 00 01`（或 `00 00 01`）分隔。用于 MP4 之外的裸码流、rtsp 等。
- **AVCC**：每个 NAL 用 **4 字节长度前缀**（表示 NAL 长度）分隔，没有起始码。用于 MP4、FLV/RTMP。
- 为什么要转？**FLV/RTMP 用 AVCC 格式**，MPP 输出 Annex-B，所以要转。
- `ParseAnnexB`：按起始码切出每个 NAL；回调里写 4 字节大端长度 + NAL 数据。

**面试点**：Annex-B 和 AVCC 的区别？为什么 FLV 要 AVCC？（AVCC 不用扫描起始码，长度前缀可以直接定位每个 NAL，解码器解析更高效。）

### 5.3.4 准备 extradata（SPS/PPS 转 AVCC）

```cpp
bool BuildAvccExtradata(const uint8_t* sps_pps, size_t size, std::vector<uint8_t>& out) {
    // 解析 Annex-B，找出 SPS（type 7）和 PPS（type 8）
    ParseAnnexB(sps_pps, size, [&](const uint8_t* nal, size_t len) {
        int type = nal[0] & 0x1F;   // NAL 头低 5 位是 NAL 类型
        if (type == 7) { sps_list.push_back(nal); ... }   // SPS
        else if (type == 8) { pps_list.push_back(nal); ... }  // PPS
    });

    // 构造 AVCDecoderConfigurationRecord（AVCC 头）
    out.push_back(0x01);                       // configurationVersion
    out.push_back(sps[1]);                     // profile
    out.push_back(sps[2]);                     // compatibility
    out.push_back(sps[3]);                     // level
    out.push_back(0xFF);                       // lengthSizeMinusOne(3) | 111100
    out.push_back(0xE0 | sps_count);           // SPS 数量
    // 每个 SPS：2 字节长度 + 数据
    ...
    out.push_back(pps_count);                  // PPS 数量
    // 每个 PPS：2 字节长度 + 数据
}
```

**逐行讲解**：
- `nal[0] & 0x1F`：NAL 头的**低 5 位**是 NAL 类型（7=SPS，8=PPS，5=IDR 关键帧）。
- `AVCDecoderConfigurationRecord`：这是 AVCC 格式的"配置记录"，解码器初始化需要它（包含 profile、level、SPS/PPS）。
- `0xFF`：`lengthSizeMinusOne=3`（用 4 字节长度）+ `111100`（保留位）。
