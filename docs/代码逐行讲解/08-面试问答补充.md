## 1. shared_ptr 是线程安全的吗？（必考，要分三层答）

**标准答案**：**控制块（引用计数）线程安全，但 shared_ptr 实例本身和被管理的对象都不安全。**

分三层：

| 层面 | 是否安全 | 说明 |
|------|---------|------|
| 控制块（引用计数） | ✅ 安全 | 内部用 `std::atomic::fetch_add`，增计数 `memory_order_relaxed`，减计数 `memory_order_acq_rel`（减到 0 要释放对象，需保证可见性） |
| shared_ptr 实例本身 | ❌ 不安全 | 多线程同时**读**安全，但有线程**写**（reset/赋值/移动）必须加锁。因为 shared_ptr 有「指针 + 计数」两个成员，两步赋值不能原子化 |
| 被管理的对象 | ❌ 不安全 | shared_ptr 只管生命周期，对象内部并发访问要对象自己加锁 |

**安全做法**：
1. 每个线程持有自己的 shared_ptr 副本（值传递，拷贝时原子 +1）。
2. 修改全局 shared_ptr 用 mutex，或 C++20 用 `std::atomic<std::shared_ptr<T>>`。
3. 对象内部并发访问需对象自身加锁。

> 本项目里 `FramePtr` 就是 shared_ptr。它在各队列间传递时是「值传递副本」（拷贝引用计数 +1），所以帧的引用计数是线程安全的；但 Frame 里的 `detection` 字段是推理线程写、编码线程读，靠的是「流水线顺序」（推理完了才入 enc_q），不是锁。

## 2. V4L2 四种内存类型（高频）

| 类型 | 内存所有者 | 拷贝 | 用途 |
|------|-----------|------|------|
| `V4L2_MEMORY_MMAP` | 内核分配 | 零拷贝（mmap） | 常规采集 |
| `V4L2_MEMORY_USERPTR` | 用户分配 | 至少一次拷贝 | 用户控制内存 |
| `V4L2_MEMORY_OVERLAY` | 显示硬件 | 零拷贝 | 视频叠加 |
| `V4L2_MEMORY_DMABUF` | 任意（共享） | 零拷贝 | 跨设备硬件流水线 |

**MMAP vs DMABUF**：MMAP 解决「摄像头→用户空间」零拷贝；DMABUF 解决「摄像头→GPU/编码器」**跨设备**零拷贝（fd 传物理内存访问权）。

> 本项目用的是 **MMAP**（mmap 映射访问），**EXPBUF 导出 fd 给 RGA**（跨设备），两者结合。

## 3. H.264 的 NALU 类型 + 关键帧（高频）

| NAL type | 内容 |
|---|---|
| 1 | 非 IDR 图像片段（P/B 帧） |
| 5 | IDR 图像（关键帧，I 帧） |
| 6 | SEI（补充增强信息） |
| 7 | SPS（序列参数集） |
| 8 | PPS（图像参数集） |

- **IDR 帧**：GOP 起始关键帧，解码器遇到 IDR 清空参考帧缓存（所以拉流端必须等 IDR 才能出画面）。
- **GOP 结构影响首播时间**：I 帧间隔越大，拉流端等第一个关键帧越久，首屏越慢。
- 本项目 `gop_size=10`（25fps 下 0.4 秒一个关键帧），兼顾首播速度和码率。

## 4. 码率控制 CBR / VBR / CRF（高频）

| 模式 | 全称 | 特点 | 适用 |
|------|------|------|------|
| CBR | Constant Bitrate 恒定码率 | 码率恒定，带宽可预测 | 直播、实时推流（本项目硬编用 CBR） |
| VBR | Variable Bitrate 可变码率 | 码率随画面复杂度变，质量稳定 | 存储、点播 |
| CRF | Constant Rate Factor 恒定质量因子 | 恒定质量，码率不可预测 | 离线编码、追求质量 |

## 5. DTS 与 PTS（高频）

- **PTS（Presentation Time Stamp）**：显示时间戳，这一帧**什么时候显示**。
- **DTS（Decode Time Stamp）**：解码时间戳，这一帧**什么时候解码**。
- 有 B 帧时，**解码顺序 ≠ 显示顺序**（B 帧要参考前后帧，所以先解码后面的 P 帧再解码 B 帧），所以 PTS 和 DTS 不一致。
- **本项目 `max_b_frames=0`（无 B 帧）**，所以 PTS == DTS（`dst_frame_->pts = pts_++`，编码包的 pts 和 dts 相同）。

## 6. 为什么视频会议不用 HLS？

HLS 是 HTTP 切片文件（TS），端到端延迟 **10~30 秒**，视频会议要求 < 几百毫秒，不可接受。视频会议用 WebRTC（延迟 < 1 秒），直播用 RTMP（1~3 秒）。

## 7. 音视频同步的时钟策略（高频）

常见策略：
- **以音频为主时钟**（audio master）：视频帧对齐音频时钟（人耳对声音断续敏感）。
- **以视频为主时钟**。
- **外部时钟**：如系统时间。

本项目是「纯视频 + 静音 AAC」，静音音轨时间戳跟随视频对齐（`WriteSilentAudio` 按视频 pts 换算音频采样数），保证 mediamtx 正常转发。

## 8. 帧内预测 vs 帧间预测（H.264 核心）

- **帧内预测（Intra）**：基于当前帧相邻已编码像素做空间域预测，消除**空间冗余**，用于 I 帧。I 帧可独立解码。
- **帧间预测（Inter）**：基于前后帧做运动估计/运动补偿，消除**时间冗余**，用于 P/B 帧。P/B 帧要参考其他帧，不能独立解码。
- 为什么 I 帧大 P 帧小：I 帧只靠帧内预测（压缩率低），P 帧靠帧间（只传运动矢量 + 残差，压缩率高）。

## 9. 为什么这个项目用「丢最旧」而不是「丢最新」？

实时视频场景，**延迟比完整性重要**。丢最旧保证队列里永远是「最新」的帧，推出去的画面实时；如果丢最新（阻塞生产者），延迟会越积越大。

## 10. 如果让你优化这个项目，你会怎么做？（开放题）

1. **全链路零拷贝**：当前 MPP 编码还有一次 memcpy（把 NV12 拷进 MPP buffer），可改成 `mpp_buffer_import` 导入 V4L2 的 dma-buf fd，实现采集→推理→编码全程零拷贝。
2. **降低延迟**：稳帧器可改成「有帧立即透传」，减少 40ms 节拍延迟（但需处理帧率波动）。
3. **多路并发**：当前单路，可改多路（多摄像头）。
4. **更好的 NMS**：当前 O(n²) 朴素 NMS，候选框多时可用排序 + 剪枝优化。
5. **内存池**：Frame 反复 new/delete，可用对象池减少分配。

## 11. 怎么测这个项目的延迟？（方法题）

1. **板端侧延迟**：在代码里记录 `capture_timestamp`（采集时刻），在推流前算 `now - capture_timestamp`，就是 pipeline 内部延迟（实测 ~50-60ms）。
2. **端到端延迟**：摄像头对着一个毫秒级计时器，拉流端看画面显示的时间 vs 真实时间，差值就是端到端延迟。
3. **启动延迟**：测拉流端「连接 → 出第一帧」的时间（受 GOP 关键帧间隔 + 客户端缓冲影响）。

## 12. 内存泄漏 / 段错误怎么排查？（通用题）

- **内存泄漏**：Valgrind（`valgrind --leak-check=full`）、AddressSanitizer（`-fsanitize=address`）。
- **段错误**：core dump + gdb（`gdb -c core ./bin` + `bt` 看调用栈）；或用 ASan 定位越界。
- **本项目遇到过的段错误**：① NV12 前处理 UV 双重偏移导致越界读（已修）；② 板端 AAC 编码器版本错配段错误（改用硬编码静音帧绕过）；③ 改头文件后没 make clean 导致新旧 .o 布局不一致（Makefile 不跟踪头文件依赖）。

## 13. 为什么用 C++17 而不是更老/更新？

- `if constexpr`（config.cpp 的类型转换）、结构化绑定、`std::optional` 等 C++17 特性。
- 比 C++11/14 更现代，比 C++20 更成熟（板端工具链 GCC 11 完整支持 C++17）。
- 项目 `Makefile` 用 `-std=c++17`。
